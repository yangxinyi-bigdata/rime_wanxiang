# Rime 输入法引擎集成大语言模型的架构蓝图


## 第一部分：执行摘要与架构愿景

### 1.1 问题陈述
核心挑战在于，如何将一个远程的、可能具有高延迟且以流式响应的大语言模型（LLM）集成到 Rime 输入法引擎（IME）中。Rime 作为一个实时的、低延迟的 C++ 应用程序 1，其集成方案必须提供无缝的用户体验，将 AI 生成的文本作为原生候选词呈现，同时不损害输入法本身的性能和稳定性。
### 1.2 推荐架构：混合代理模型
本报告主张采用一种混合代理架构。其核心组件包括：

- **`librime-lua` 翻译器（Translator）**：在 Rime 进程内部扮演一个轻量级客户端的角色 3。其唯一职责是与一个本地代理服务进行通信。
- **本地持久化 Python 代理服务器**：作为一个独立的后台进程运行。该服务器利用 Python 的 `asyncio` 库 5 来管理所有外部网络 I/O 和复杂的业务逻辑。
### 1.3 架构合理性论证
此架构选择是基于对系统各部分需求的深刻理解而做出的，旨在实现稳健性、性能和可维护性的最佳平衡。

- **解耦与稳健性**：将网络操作隔离在一个独立的进程中，可以有效防止网络延迟、请求超时或 LLM API 错误等问题冻结甚至导致 Rime 输入法主程序崩溃。Rime 进程的通信对象始终是一个低延迟的本地套接字（socket）8，从而保证了核心输入体验的流畅性。
- **发挥生态系统优势**：该模型为每个任务选择了最合适的工具。它利用 Rime 强大的 YAML 配置系统 10 和 Lua 脚本接口 3 实现与输入法引擎的原生集成；同时，它借助 Python 成熟的生态系统来处理复杂的异步操作，例如使用强大的库来处理流式 HTTP 请求 13 和与 LLM API 进行交互 15。
- **可维护性与可扩展性**：所有复杂逻辑，包括提示词工程（prompt engineering）、API 密钥管理、错误处理、在不同 LLM 之间切换等，都集中在 Python 代理中。这部分逻辑可以独立于 Rime 配置进行更新和测试，极大地简化了开发和维护的生命周期。

这种架构选择并非偶然，而是对一个根本性矛盾进行权衡的结果：一个要求实时响应的用户界面（输入法）和一个非确定性的、高延迟的网络服务（LLM）之间的矛盾。如果采用单体式架构，即将所有网络和业务逻辑都放在 Rime 进程内的 Lua 脚本中，那么整个系统将变得非常脆弱。具体分析如下：Rime 作为一个性能关键型应用，必须以最小的延迟处理用户输入 2。而 LLM API 调用是网络密集型的，完成一次调用可能需要数秒钟，且延迟不可预测 13。尽管流式传输（streaming）改善了用户的感知延迟，但并未消除其固有的异步性。Lua 语言虽然功能强大，但其标准库在网络编程方面相对基础。在 Lua 中实现一个健壮的、非阻塞的、能够处理流式服务器发送事件（SSE）并包含完整错误处理和重试逻辑的客户端，是一项巨大的工程挑战，极易引入阻塞调用或将 Bug 带入关键的 Rime 进程中 18。相比之下，Python 的 `asyncio` 5 以及 `httpx`、`sseclient` 14 等库正是为解决此类问题而设计的，并由庞大的社区维护。因此，将关注点分离——让 Rime 负责输入处理，Lua 负责简单的进程间通信（IPC），而 Python 负责复杂的网络 I/O——是实现该功能最稳健、最高效的路径。这种架构模式不仅最小化了风险和开发工作量，还为 Rime 建立了一个通用的“服务桥梁”，未来可以轻松扩展，通过同一个 Python 代理为输入法提供其他在线服务（如实时翻译、语法检查等），而无需对 Lua 插件进行大的改动。

## 第二部分：组件深入分析之 `librime-lua` 翻译器


### 2.1 安装与配置
首先，需要确保用户的 Rime 环境已安装 `librime-lua` 插件，并能被引擎正确加载 2。随后，通过修改用户的输入方案配置文件（如 `luna_pinyin.custom.yaml`）来启用这个 Lua 翻译器。具体操作是在 `engine/translators` 列表中添加 `lua_translator@<function_name>`，其中 `<function_name>` 是在 `rime.lua` 脚本中定义的函数名 12。

对于 `luasocket` 等外部 Lua 模块的依赖管理，Rime 用户数据目录下的 `rime.lua` 文件是所有 Lua 脚本的入口点。可以通过在脚本中修改 Lua 的 `package.path` 变量，或将模块文件放置在 Rime 的 Lua 环境已知的搜索路径中，来实现模块的加载 25。
### 2.2 触发逻辑与状态管理
在 Rime 中，Lua 翻译器函数会接收到 `input`（当前输入码）和 `seg`（分段信息）等参数 24。为了实现复杂的交互，翻译器内部必须实现一个简单的状态机，其关键状态包括：

`IDLE`（空闲）、`REQUEST_SENT`（已发送请求）、`STREAMING_RESPONSE`（正在接收流式响应）。

向 Python 代理发送请求的触发条件应是可配置的，具体可实现为：

- **手动触发**：在 `default.custom.yaml` 中定义一个特定的快捷键，该快捷键的功能是设置一个标志位，Lua 翻译器在每次被调用时检查此标志位。
- **自动触发**：基于 `input` 字符串的内容，例如在输入达到一定长度后，或在输入了句末标点符号时自动触发。此方式需要实现精细的“去抖”（debouncing）逻辑，以避免因用户快速输入而向代理发送大量冗余请求。
### 2.3 使用 `luasocket` 实现 IPC 客户端
Lua 脚本将使用 `require("socket")` 9 来创建一个 TCP 客户端套接字，并尝试连接到本地的 Python 代理服务（例如 127.0.0.1:PORT`）。

一个至关重要的实现细节是，该套接字**必须**被设置为非阻塞模式（例如通过 `socket:settimeout(0)`），以防止任何网络操作（如连接、接收数据）阻塞 Rime 的主线程，从而导致输入法卡顿 21。

当触发条件满足时，Lua 脚本会将请求（例如，一个包含当前输入码的 JSON 字符串）序列化，并根据后续定义的 IPC 协议发送给代理。由于 Rime 引擎会频繁调用翻译器函数，脚本可以在每次被调用时，通过非阻塞的 `socket:receive()` 检查是否有来自代理的新数据。

脚本还必须优雅地处理连接失败的情况。如果与代理的连接断开，它应尝试以一定的策略（如指数退避）进行重连，并能正确处理 `luasocket` 调用可能返回的 `timeout` 等错误 32。
### 2.4 动态候选词生成
当从代理接收到数据块时，Lua 脚本会对其进行解析。整个集成的核心在于使用 `yield(Candidate("ai_suggestion", seg.start, seg._end, text, "✨AI"))` 这行代码，它能将 AI 的回复动态地注入到 Rime 的候选词列表中 12。

为了实现流式更新的效果，即让候选词看起来是“生长”出来的，而不是每来一个词元（token）就增加一个新候选词，必须采用更精巧的逻辑。一个简单的实现会因为产生大量候选词而导致界面混乱。稳健的方法是，在 `yield` 第一个词元后，保存该候选对象（Candidate object）的引用，在接收到后续词元时，直接更新该对象的 `text` 属性。或者，在每次收到新词元时，清空当前上下文并重新 `yield` 一个包含至今为止所有词元的、唯一的 AI 候选词。

理解 Lua 翻译器在 Rime 中的工作方式是实现此功能的关键。它并非一个一次性执行并返回结果的普通函数，而是一个协程（coroutine）。`yield` 关键字不仅仅是返回一个值，它实际上是暂停了函数的执行，将控制权交还给 Rime 引擎，并准备在未来某个时刻从暂停点恢复执行。这个机制是实现异步风格操作的基础。

具体流程如下：

1. Rime 引擎处理用户输入，并调用已注册的翻译器 12。

2. 我们的 Lua 翻译器被调用。它首先检查其非阻塞套接字上是否有数据。如果没有，它便直接返回，将控制权还给引擎。

3. 如果套接字上有数据（即来自 LLM 的一个词元），它便处理这些数据。

4. 接着，它调用 `yield(Candidate(...))` 29。这个操作同时完成两件事：向引擎提供一个用于显示的候选词，并

   **暂停** Lua 脚本的执行。

5. Rime 引擎继续其事件循环。在后续的某个事件（如用户再次按键，或某个内部计时器触发）中，它会从上次暂停的地方**恢复**该翻译器协程的执行。

这个“检查套接字 -> 生成候选 -> 暂停 -> 恢复”的循环，使得 Lua 脚本可以在不阻塞 Rime 主事件循环的前提下，从一个数据流中增量地构建候选词。这一模式不仅适用于 LLM 集成，也为在 Rime 中实现任何其他动态或异步功能（如实时词典查询、网络搜索等）提供了范本。
## 第三部分：组件深入分析之异步 Python 代理服务器


### 3.1 基于 `asyncio` 的服务器基础
代理服务器的核心是利用 `asyncio.start_server` 创建一个 TCP 套接字服务器，监听在本地的一个端口（如 `8888`）上 5。主服务器循环将异步地接受来自 Rime Lua 插件的连接。每一个客户端连接都将由一个专门的异步任务（通过 asyncio.create_task` 创建）来处理。这种设计使得服务器能够并发处理多个 Rime 客户端（例如，当用户打开了多个需要输入法的应用程序时）。
### 3.2 LLM API 通信
代理服务器将使用官方的 OpenAI Python 库或针对其他 LLM 的类似库。关键是在 API 调用中设置 `stream=True` 参数（例如在 `client.chat.completions.create` 中），以启用流式响应 15。

API 的响应将是一个服务器发送事件（SSE）的迭代器。Python 代码通过 `async for chunk in stream:` 循环遍历这个迭代器，在每个词元（token）到达时立即进行处理 13。数据流的结束通常由一个特殊的标记来指示（例如，在旧版 OpenAI API 中是 `` 字符串，在新版 API 的最后一个数据块中是 `finish_reason` 字段 14）。代理服务器必须能检测到这个结束标记，以便向 Lua 客户端发送流结束的信号。
### 3.3 消息代理逻辑
这是代理服务器的核心业务逻辑。针对每个客户端连接的处理器函数将执行以下步骤：

1. 进入一个循环，异步地从客户端套接字读取数据。
2. 根据下文定义的 IPC 协议解析来自 Lua 插件的请求消息。
3. 在收到一个有效的查询请求后，构造合适的提示词，并向 LLM API 发起流式调用。
4. 当从 LLM 数据流中接收到每个 `chunk` 时，将其序列化为 IPC 格式，并立即写回给对应的客户端套接字（通过 `writer.write(data); await writer.drain()`）5。
5. 当 LLM 数据流结束后，向 Lua 客户端发送一个流结束（end-of-stream）的 IPC 消息。

此外，如果 Rime 客户端断开连接或发送了一个“取消”消息，代理服务器必须能立即终止相应的 LLM API 请求，并清理相关的异步任务，以避免资源浪费。
### 3.4 进程间通信（IPC）协议
一个稳健的 IPC 协议对于 Lua 客户端和 Python 代理之间的可靠通信至关重要。

**推荐协议：长度前缀 + JSON**

- **头部（Header）**：一个固定大小（例如 4 字节）的无符号整数，用网络字节序（大端序）表示后续消息体的长度。Python 的 `struct.pack('!I', length)` 和 `struct.unpack('!I', data)` 是实现此功能的理想工具 38。Lua 端需要实现相应的打包/解包逻辑。
- **载荷（Payload）**：一个 UTF-8 编码的 JSON 字符串。这为传输复杂的结构化数据提供了极大的灵活性。

一个正式的协议定义能够消除歧义，充当 Lua 客户端和 Python 服务器开发者之间的契约。与使用特定分隔符的协议相比，长度前缀协议更为稳健，因为它能正确处理可能包含分隔符本身的任意二进制数据，是基于 TCP 流的通信中一种标准且可靠的解决方案 40。
#### 表 3.1：IPC 消息协议定义
| 消息类型        | 方向          | 载荷 (JSON) 结构                                   | 描述                                                         |
| --------------- | ------------- | -------------------------------------------------- | ------------------------------------------------------------ |
| `QUERY`         | Lua -> Python | `{"type": "query", "id": "...", "text": "..."}`    | 从 Rime 发送，为给定文本请求 AI 补全。`id` 是唯一的请求标识符。 |
| `CANCEL`        | Lua -> Python | `{"type": "cancel", "id": "..."}`                  | 从 Rime 发送，用于取消一个正在进行中的请求。                 |
| `TOKEN`         | Python -> Lua | `{"type": "token", "id": "...", "text": "..."}`    | 从 LLM 流式响应中得到的单个词元。                            |
| `END_OF_STREAM` | Python -> Lua | `{"type": "eos", "id": "...", "reason": "..."}`    | 标志着指定请求的数据流结束。`reason` 可以是 `done`、`error` 或 `cancelled`。 |
| `ERROR`         | Python -> Lua | `{"type": "error", "id": "...", "message": "..."}` | 报告来自代理服务器的错误（例如 API 密钥无效）。              |

Python 代理不仅仅是一个简单的中继，它是一个**有状态的消息代理**。它必须并发地管理多种状态：与每个 Rime 客户端的套接字连接状态，以及为每个活动查询与 LLM API 建立的流式 HTTP 连接状态。

设想一个场景：

1. 用户快速输入，触发一个 `QUERY` 请求（请求 A）。
2. 代理收到请求，创建一个任务，并向 LLM API 打开一个数据流。
3. 用户立即按退格键修改输入，这会生成一个针对请求 A 的 `CANCEL` 消息，以及一个针对新内容的新 `QUERY` 请求（请求 B）。
4. 代理必须能够准确地将收到的 `CANCEL` 消息映射到处理请求 A 的任务，终止其 LLM 数据流并进行清理。
5. 同时，它必须为请求 B 启动一个新任务和新的数据流。
6. 来自请求 B 数据流的词元必须被正确地路由回客户端套接字，不能与请求 A 的任何残留数据混淆。

要实现这一点，代理内部需要一个映射结构，例如一个将 `request_id` 映射到 `(client_writer, llm_stream_task)` 元组的字典。这种机制确保了数据的正确路由和取消请求的精确执行。这种状态管理的复杂性，正是采用独立代理架构而非在 Rime 进程内实现所有逻辑的最有力论据。
## 第四部分：用户交互与状态管理的穷尽式分析


### 4.1 AI 写作状态机
为了满足用户对于稳健逻辑的需求，我们必须将整个交互过程建模为一个状态机。该状态机由 Lua 翻译器在 Rime 内部进行管理，可以使用一个全局表（table）来存储当前状态。

**状态定义**：

- `IDLE`：空闲状态，无输入或 AI 交互。
- `COMPOSING`：用户正在输入，但未触发 AI 请求。显示标准的 Rime 候选词。
- `AWAITING_AI`：已向代理发送请求，但尚未收到任何响应。UI 可显示“加载中”提示。
- `AI_STREAMING`：正在从代理接收词元流。AI 候选词可见且正在动态更新。
- `AI_COMPLETE`：词元流结束。AI 候选词变为一个静态、可选择的选项。
- `AI_SELECTED`：用户通过方向键或鼠标悬停等方式，高亮选中了 AI 候选词。

下表是本报告的核心部分，它为编程实现提供了一份详尽、可操作的指南。该矩阵将每一种可能的用户输入，根据当前所处的状态，映射到特定的系统响应。这种方法强制对每一种交互可能性进行严谨和系统的分析，是“覆盖各种分支”和“减少 bug”的唯一途径，将设计从抽象概念转化为具体、可测试的规范。

## 第五部分：稳健性、错误处理与跨平台部署


### 5.1 网络与 API 错误处理
- **代理端**：Python 代理必须将所有对 LLM API 的调用包装在 `try...except` 块中，以捕获连接错误、超时以及 HTTP 状态码错误（如 401 未授权、429 请求速率超限、500 服务器错误）。这些错误应被详细记录，并通过 `ERROR` 类型的 IPC 消息传播给 Lua 客户端。
- **客户端**：Lua 翻译器必须能优雅地处理 `ERROR` 消息，例如，可以在候选列表中显示一个短暂的错误提示，然后自动回退到 `COMPOSING` 状态。
- **与代理的连接**：Lua 脚本必须处理 Python 代理未运行或崩溃的情况。它应该采用指数退避等策略尝试重连，并在代理不可用时临时禁用 AI 功能。
### 5.2 部署与生命周期管理
- **代理进程**：Python 代理服务器需要在用户登录时自动启动，并作为后台进程或服务运行。
  - **Windows**：可使用 PyInstaller 等工具将 Python 脚本打包成可执行文件，并将其添加到用户的“启动”文件夹或创建为 Windows 服务。
  - **macOS**：应使用 `launchd` 创建一个用户代理（User Agent），以确保代理进程的持久运行。
  - **Linux**：应使用 `systemd` 用户服务（user service）进行管理。
### 5.3 跨平台输入模拟（用于上屏文本）
尽管 Rime 自身处理了大部分文本插入，但在某些情况下，如果通过 Rime 的原生机制上屏长文本或多行文本存在困难，可能需要一个备用方案：以编程方式模拟粘贴操作。这部分逻辑需要平台特定的实现，可以在 Python 代理中完成。

- **识别操作系统**：使用 `platform.system()`（其返回值在 Windows、macOS、Linux 上分别为 `'Windows'`, `'Darwin'`, `'Linux'`）来判断当前运行的操作系统 42。
- **剪贴板操作**：使用如 `pyperclip` 这样的跨平台库将文本复制到系统剪贴板 46。
- **模拟按键**：使用如 `pynput` 或 `pyautogui` 这样的库来模拟 `Ctrl+V` 或 `Cmd+V` 组合键的按下 50。
- **macOS 权限问题**：在 macOS 上，这是一个重大的障碍。任何希望控制键盘或鼠标的应用程序都必须获得用户在“系统设置”中授予的“辅助功能”权限 54。因此，部署过程必须清晰地引导用户如何为 Python 代理的可执行文件（或运行它的终端）授予此权限。

将 AI 文本上屏是另一个潜在的故障点和平台相关的复杂性来源。首选方案是利用 Rime 的原生上屏机制。然而，如果该机制无法很好地处理任意长度或多行的字符串，那么模拟用户粘贴就成了备用方案。这个备用方案引入了新的依赖，并可能给用户带来不便（尤其是在 macOS 上）。

具体来说，当用户选择 AI 候选词后，理想的流程是 Lua 翻译器向 Rime 引擎发送一个信号，要求其上屏完整的文本。这是最“干净”的方式。但如果 Rime 的内部提交 API 存在限制或难以控制，备选方案就是模拟用户输入：复制文本，然后粘贴。这种模拟操作不能在 Rime 进程的沙箱内完成，必须由具有相应权限的外部进程（即 Python 代理）执行。这就要求代理安装了剪贴板 (`pyperclip`) 和键盘控制 (`pynput`) 库 46。在 macOS 上，这将立即触发对“辅助功能”权限的需求，这是一个主要的用户体验痛点，因为用户必须手动进入系统设置进行授权 54。因此，一个关键的设计原则是：

**始终优先使用宿主应用程序的原生 API，而不是模拟用户输入**。模拟方案应作为最后的备选，因为它更脆弱，并且由于权限要求而创造了更差的用户体验。开发计划应优先探索 Rime 原生上屏能力的实现。
## 第六部分：配置、安全与未来工作


### 6.1 用户配置
应充分利用 Rime 的 `*.custom.yaml` 系统来管理所有面向用户的设置 10。可以在配置文件中定义一个专门的配置节，例如 

`ai_assistant:`。

**可配置选项**应包括：`enabled: true/false`（启用/禁用功能）、`trigger: manual/auto`（触发方式）、`auto_trigger_length: 5`（自动触发长度）、`llm_model: "gpt-4-turbo"`（使用的模型）、`proxy_port: 8888`（代理端口）等。Lua 脚本将通过 `env.engine.context:get_option("ai_assistant/enabled")` 等方式从引擎上下文中读取这些配置。
### 6.2 安全性
- **API 密钥管理**：LLM 的 API 密钥是高度敏感的信息，**绝对不能**以明文形式存储在任何 YAML 配置文件中。
- Python 代理应从一个安全的位置读取 API 密钥，例如操作系统的环境变量（`OPENAI_API_KEY`），或者一个位于用户主目录下、权限受限的专用配置文件（如 `~/.config/rime_ai/config.ini`）。
### 6.3 实施路线图
1. **阶段一：核心后端**：开发 Python `asyncio` 代理。实现 TCP 服务器、IPC 协议和流式 LLM 客户端。独立测试该组件。
2. **阶段二：基础集成**：开发 `librime-lua` 翻译器。实现非阻塞套接字客户端和基础的 `yield(Candidate(...))` 逻辑。首先实现一次性的（非流式）请求/响应循环。
3. **阶段三：流式处理与 UI**：实现完整的流式逻辑，包括 Lua 中的候选词更新机制和 Python 中的消息代理逻辑。
4. **阶段四：用户交互与状态机**：根据第四部分的“用户操作处理矩阵”，实现完整的状态机和交互逻辑，使交互体验变得稳健。
5. **阶段五：错误处理与部署**：实现全面的错误处理机制，并为 Windows、macOS 和 Linux 创建部署脚本或安装程序。
## 第七部分：结论
本报告提出了一种混合代理架构，用于将大语言模型功能集成到 Rime 输入法引擎中。该架构通过将实时性要求高的输入前端与延迟不定的网络后端进行解耦，在稳健性、可维护性和用户体验之间取得了平衡。报告详细阐述了 `librime-lua` 客户端和 Python `asyncio` 代理服务器两个核心组件的设计与实现要点，并提供了一套基于状态机的、穷尽式的用户交互处理逻辑，为项目的工程实现提供了明确的蓝图。通过仔细分离关注点、定义清晰的接口和状态转换，可以成功地在 Rime 框架内构建一个强大而稳定的 AI 辅助输入体验。本报告为实现这一目标提供了全面的技术规划，旨在降低开发风险并指明一条清晰的前进道路。
